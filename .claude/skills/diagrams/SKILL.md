Produce a single living document, `plan/diagrams.md`, holding the project
architecture at three zoom levels in plain-text (ASCII) diagrams. It is
**idempotent**: create the file if absent, otherwise refresh it in place so
the diagrams always match the latest state of `plan/` and `DECISIONS.md`.

No Mermaid, no images — ASCII text diagrams that live in the repo and
render anywhere. Representation priority throughout: **diagram > table >
minimal prose**.

## Ground it first — read the source of truth, don't recall it

Every status marker must be derived, not remembered:

1. `plan/00-context.md` — the status table (which phases are done / in
   progress) and the arc.
2. The phase files (`plan/01…04`) — ticked checkboxes and gate results tell
   you what is actually built vs specced.
3. `plan/05-fast-follow.md` — the FF register: the evaluated-but-deferred
   ideas and where each attaches to the pipeline.
4. `DECISIONS.md` — gate passes, retired concepts, anything that flips a
   marker.

If a stage's state is genuinely ambiguous, mark it with the nearest state
and say so in a one-line note rather than guessing confidently.

## The status key — Levels 2 and 3 ONLY

Level 1 is conceptual and timeless: **do not put status markers on it.**
Levels 2 and 3 open with this key and use it on every stage:

```
🟩 Built     — code exists in the repo, its gate/verification passed
🟦 Planned   — specced on the critical path, not yet built
🟨 Proposed  — evaluated, deferred OFF the critical path (the FF register)
◐  scaffolded — code exists but has not been verified yet (a sub-state of Built)
```

Emoji are the colour coding (ANSI doesn't render in the target medium).
Keep the key block identical every time so a reader learns it once.

## The three levels

**Level 1 — the whole idea (NO key).** The biggest concepts and how they
flow into each other: the world (camera/video) → a per-pixel judgement of
seen / filled-in / flashing → the viewer's screen, with the comparison view
as the honesty check. Three or four boxes, plain nouns, one-line captions.
Timeless — it does not change when a phase ships, so it carries no status
markers.

**Level 2 — the pipeline (keyed).** The frame path drawn as a single
annotated spine: background source → texture upload (`renderer.js`, with
the per-frame uniforms from `controls.js`/`config.js`) → the shader's
stages (field mask → fill-in → photopsia net → edge rings → split view) →
screen. Attach the 🟨 proposed extensions (FF register) at the stage each
belongs to — gaze tracking upstream, WebGL2/FBO branches at the texture
stage, motion boost at the island-rendering stage, etc. Follow the spine
with a compact table keying each 🟨 item to *where it attaches*, *what it
adds*, and *its revisit-trigger* (straight from the FF register).

**Level 3 — per-stage deep dive (keyed).** One focused
`inputs → transform → outputs` diagram per shader/renderer stage, each
headed with its status marker, arrows carrying plain-language cargo labels.
Note attached proposed branches inline. Give structurally-new proposed
items their own diagram, clearly marked 🟨. For 🟦 planned stages, draw the
*intended* shape from the plan and say it's not built.

## Writing / updating the file

- Header block: a one-line note that the file is generated by `/diagrams`,
  that the source of truth is `plan/` + `DECISIONS.md`, and a **Last
  updated** date (convert relative dates to absolute).
- On **update**: regenerate all three levels from the current source of
  truth, then report to chat **what changed since the previous version** —
  which markers flipped, which FF items moved. This is the plan-sync habit
  applied to the diagrams.
- Keep arrows labelled with what actually flows; define any jargon at first
  use; keep prose to the minimum the diagrams and tables can't carry.

## Finish with

- Report the path and the marker changes since last run.
- Offer to commit (`plan/diagrams.md`), with a message noting the state it
  now reflects. Pairs naturally with `plan-sync` — run this right after, so
  the diagrams reflect the freshly-synced plan.
